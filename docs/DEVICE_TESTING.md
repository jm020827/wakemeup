# 실기기 검증

## 필수 기록

| 항목 | 기록 예 |
| --- | --- |
| 기종·OS | 휴대폰 모델/Android 버전, 워치 모델/Wear OS/Health Services 버전 |
| 수면 상태 지원 | 워치 지원 확인과 휴대폰 표시, 신체 활동 권한 |
| 감시 등록 | 휴대폰 ‘입면 정보를 기다리고 있어요’, 워치 ‘수면 감시 중’ |
| 실제 입면 기준 | 본인이 기록한 입면 근사 시각과 워치 추정 차이 |
| 수신 지연 | onsetAt → watchReceivedAt → receivedAt; 수면 기록 CSV |
| 목표 알람 | onsetAt + targetMinutes; 수신시각 기준 계산 여부 금지 |
| 소리·진동 | 잠금, 절전, 방해금지/수면모드 각각 확인 |
| 실행 오차 | RING 로그의 예약·실행 시각과 오차(ms) |
| 배터리 | 휴대폰·워치 각각 감시 전후 잔량과 경과시간 |

## 실제 취침 테스트

1. 같은 서명의 두 APK를 설치하고 워치 권한·수면 지원을 확인합니다.
2. 휴대폰 정확한 알람·알림·기상 알람 채널을 허용하고 알람 볼륨을 확인합니다. 필요한 경우 전체 화면 알람 접근도 허용합니다.
3. 목표 시간을 선택하고 고정 예비 알람을 켭니다. 0.1.2부터 일반 사용자에게 별도 검증 모드나 메모 입력을 요구하지 않습니다.
4. 취침 전 감시를 시작합니다. 버튼 시각이 추정 입면으로 표시되면 실패입니다.
5. 기상 전 수면 이벤트가 도착하는지 확인합니다. 워치 미지원 또는 기상 후 전달만 확인되면 자동 알람을 활성화하지 않습니다.
6. 아침에 **수면 흐름**에서 시험한 밤을 선택해 입면·폰 수신·기상시각과 시계·타임라인을 확인합니다. 소리·진동·입면 추정 차이·배터리 잔량은 시험 기록으로 남기고, 필요하면 **설정 → 기록 내보내기**로 CSV를 내보냅니다.
7. 수면 감시 시작 하나로 목표 예약까지 진행되는지 확인합니다. 기존 메모·검증 완료·모드 전환 절차가 다시 나타나면 실패입니다.

## 연결·복구 시험

| 시험 | 기대 결과 |
| --- | --- |
| 동일 이벤트 재전달 | 첫 onsetAt와 기존 목표 유지, IGNORED 기록 |
| 이후 재입면 이벤트 | 첫 입면 유지, 목표 다시 계산하지 않음 |
| 다른 세션 이벤트 | 현재 세션 변경 없음 |
| 감시 후 Bluetooth/Wi-Fi 해제 | 예비 알람 유지, 정상 연결 상태로 표시하지 않음 |
| 연결 해제 중 워치 수면 이벤트 | 워치 로컬 저장; 재연결 후 원래 입면 기준 계산 |
| 휴대폰 앱 프로세스 종료 | 수신 서비스가 기록·예약; AlarmManager 예약 유지 |
| 휴대폰 재부팅 | 미래 목표 또는 예비 알람 복구; 경과한 목표를 즉시 울리지 않음 |
| 워치 재부팅 | 저장된 세션 감시 재등록; 이전 첫 입면 유지 |
| 정확한 알람/알림 권한 해제 | 필수 권한 부족 표시, 새 감시 불가; 예약 실패 시 예비 알람 교체 금지 |
| 감시 취소 후 늦은 이벤트·알람 | 세션 부활·소리·진동 없음 |
| 새 감시 세션 시작 | 이전 입면 기록은 수면 흐름에서 계속 선택 가능 |
| 다른 밤 선택 | 시계·입면·수신·알람이 모두 선택한 밤 기준 |
| 옛 검증 세션으로 0.1.2 업데이트 | 실제 입면·수신시각 유지; 자동 감시로 전환; 과거 목표를 즉시 울리지 않음 |
| 첫 실행·권한 거절 | 순서대로 권한 안내; 필수 권한 부족 시 시작 불가; 반복 팝업 없음 |

## Debug APK 이벤트 주입

`mobile/src/debug`에만 포함되는 adb 수신기로 실제 워치 없이 휴대폰 예약·출력을 검증할 수 있습니다. 주입 데이터는 실제 워치의 지원·전달 지연을 증명하지 않습니다. Release APK에는 이 수신기가 없습니다.

휴대폰 앱을 열어 정확한 알람·알림 권한을 허용하고 진행 중인 감시를 종료한 뒤 실행합니다. `PHONE_ID`는 실제 `adb devices -l`에서 확인합니다.

```bash
adb -s PHONE_ID shell am broadcast \
  -n com.wakemeup/com.wakemeup.mobile.debug.DebugScenarioReceiver \
  --es scenario delayed
```

| scenario | 주입 및 기대 결과 |
| --- | --- |
| `delayed` | 3시간 전 입면 + 6시간 목표 → 지금부터 3시간 뒤 목표 알람, 예비 교체 |
| `duplicate` | 같은 입면과 1분 후 재입면 전송 → 첫 입면 고정, 목표 하나 |
| `old` | 다른 세션 이벤트 추가 → 이전 세션 무시 |
| `late` | 6시간 1분 전 입면 → 목표 실패, 20초 뒤 예비 알람 유지 |
| `ring` | 5시간 59분 45초 전 입면 → 약 15초 뒤 목표 소리·진동·해제 UI |
| `validation` | 옛 검증 세션 호환성 시험; 앱 복구 시 실제 입면을 유지하고 자동 알람으로 전환 |
| `cancel` | 진행 중인 세션의 모든 알람 취소 |

시험 사이에 `--es scenario cancel`을 실행하거나 앱에서 감시를 종료합니다. `ring`/`late` 출력 시험은 기기의 잠금·절전·수면모드를 각각 설정해 반복합니다.

```bash
adb -s PHONE_ID shell dumpsys alarm
```

알람은 sessionId와 TARGET/BACKUP을 포함한 서로 다른 PendingIntent URI를 사용합니다. 앱의 ‘수면 기록’에서 SCHEDULED/MISSED/RING/DISMISS와 실행 오차를 확인합니다.

미래 알람을 예약한 후 두 기기의 재부팅 및 재연결 시험도 진행하세요. Android 테스트나 이벤트 주입의 성공이 실제 워치의 수면 지원·기상 전 전달·입면 정확도를 증명하지는 않습니다.
